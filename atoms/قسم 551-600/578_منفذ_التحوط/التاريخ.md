## 5.4.0 — 2026-08-27 (found during a full 304-atom audit, not assumed)

- **Blocking sqlite write on every live pair transition.** `_publish_pair`
  (the single choke point every pair mutation flows through --
  `_on_requested`, `_actual_for`, every retry and exhaustion in
  `_failure_for`) called `_persist_pairs` as a plain synchronous method,
  no `asyncio.to_thread` -- a real blocking write on every leg request,
  ack, retry, and escalation.
- **The naive fix needed a second look, same lesson as 516's.** Wrapping
  the write alone in `asyncio.to_thread` opens an await point between
  "seal the current pairs" and "commit to disk." Two pair transitions in
  quick succession (routine -- a BUY leg and a SELL leg landing back to
  back) could then have their disk writes complete out of order: an
  older, slower-to-schedule snapshot landing on disk *after* a newer one,
  silently rolling the durable pair record backward. Reproduced
  empirically in a disposable scratch copy before deciding this needed a
  lock, not just a thread: with the write threaded but unlocked, a
  2-write race lands `[['P-A','P-B'], ['P-A']]` on disk -- the newer
  state (with P-B) gets overwritten by the stale one. Fixed with a
  single atom-level `asyncio.Lock` (`self._persist_lock`) around the
  whole seal+write -- one shared file, one lock, writes now always
  commit in the order they were issued. New tests
  `test 19-20` (unnamed in this file's single-`main()` style; search
  "القفل يمنع كتابة أقدم" / "حلقة الحدث بقيت حرّة") prove both the
  ordering guarantee and that the event loop genuinely stays free during
  the write.
- **`pair_memory.seal()` only shallow-copied each pair** (`dict(v)` --
  copies the pair's own keys, not its nested `legs` sub-dict). Handing
  that to a background thread for JSON serialization, or holding a
  `snapshot()` result past the current turn, meant a concurrent handler
  mutating `pair["legs"]` could tear the write or silently change what
  gets persisted/returned. Now `copy.deepcopy`s the whole pairs dict --
  fixes both the new threaded persist path and the pre-existing
  `atom.snapshot()` aliasing.
- **`health_check` extracted to `health_view.py`** (same reasoning as
  every prior split in this atom: one atom, one job, 350-line
  constitutional cap) -- pure read of atom state, zero behavior change.
  Freed the room the lock needed; also dropped `HealthState`/
  `HealthStatus`/`STATUS_EXHAUSTED` from `atom.py`'s own imports/constants
  once nothing there referenced them anymore.
- **Three pre-existing Arabic-language comments in `atom.py`** (م3/ملف4)
  translated in place, zero behavior change.
