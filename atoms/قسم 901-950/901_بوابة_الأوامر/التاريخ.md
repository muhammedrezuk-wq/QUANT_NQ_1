## 2.7.0 — 2026-08-27 (found during a full 304-atom audit, not assumed)

- **Batch-commit fix.** `_on_pulse` committed once per whole batch, not per
  row. A `sqlite3.Error` partway through (measured trigger:
  `ParameterRegistry().approve()` inside `_apply_parameter_approval`,
  `parameter_approve` only) rolled back the commit for rows already
  published earlier in the SAME pulse -- they read PENDING again next
  pulse and were re-published. Same failure class as the 279+120/day
  regression `test_gate_command_executes_and_closes_row` already
  documents, different trigger, not closed by that fix. Now: `commit()`
  after every row. A failing row stays PENDING alone; everything before
  it in the same batch is already sealed and never replays.
- **`_to_float` no longer accepts bool.** `float(True) == 1.0` let a
  malformed `"budget": true` pass silently as budget=1.0 everywhere this
  helper feeds validation. Same exclusion `_finite_number` already had,
  now applied where it actually matters.
- **Two tests that were never run, now are.**
  `test_gate_command_executes_and_closes_row` (the historical-regression
  test itself) and `test_every_action_has_a_counter` were defined in this
  file but missing from `main()`'s `tests` list -- silently never
  executed. Added.
- New test `test_batch_commit_per_row_no_replay_on_mid_batch_failure`
  reproduces the exact failure and proves the fix. 15/15 passing,
  validator clean.
- **Not fixed, documented instead of rushed:** command-source
  authentication. Any PENDING row in `commands.db` executes as
  `OWNER_COMMAND` regardless of who wrote it; the only gate today is the
  two-step confirm at the writers (`governance/server.py`,
  `governance/telegram.py`). A real fix needs coordinated changes across
  those files plus this one -- out of scope for a same-day fix without
  risking either a broken legitimate path or a false sense of security
  from a half-built check.
